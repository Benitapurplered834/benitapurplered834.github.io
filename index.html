Have you ever seen a Dependabot or Renovate PR that updates five, ten, or twenty packages at once — and then your build fails? 💡 What is depsect?

depsect was created to solve one specific, painful problem: diagnosing failures caused by grouped dependency updates. When tools like Dependabot or Renovate bundle many package updates into a single pull request, and your build breaks, you need a way to isolate exactly which package upgrade is responsible. depsect automates this process.

It works by automatically testing each package update in the group and narrowing down the failure to a single package — just like git bisect narrows down a bad commit in a history. The result: you get a clear answer like "Your build fails because the request package was updated from 2.88.2 to 2.88.3."

🆘 Troubleshooting & FAQ

I don't know how to use command-line tools. Is that a problem?

No! depsect is designed for regular computer users and developers who prefer a visual interface. You won't need to write a single command. Just click, point, and investigate.

What if my project does not have a lockfile?

depsect works best when there is a lockfile (like package-lock.json, Cargo.lock, poetry.lock, etc.) because it helps to precisely track versions. However, depsect can still help by looking at the declared requirements and using heuristics. The results might be slightly slower, but they will still work.

Is my code safe?

Absolutely. depsect analyzes your project in a read-only way. It does not modify your package files, commit anything, or make any permanent changes. Its job is purely to observe and diagnose.

Can I use depsect with any CI/CD system?

depsect is primarily a desktop application. However, many users also run it manually on their CI server as part of a debugging session. The tool works independently of your CI provider. A GitHub Action is listed among the topics, suggesting that you can also integrate it seamlessly with your GitHub Actions workflows in the future.
